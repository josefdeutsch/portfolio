# Prospect Orchestrator — Worked Examples

These synthetic scenarios explain mechanisms described in the supplied export. Identifiers and intermediate labels are illustrative, not actual schema fields, extracted source, executed demonstrations, or new test results. Evidence IDs refer to [EVIDENCE.md](EVIDENCE.md).

## Recover a known enrichment operation after a crash

**Scenario:** company enrichment is eligible because upstream discovery evidence has committed.

| Step | Local responsibility | Recovery implication |
| --- | --- | --- |
| 1 | A short transaction checks eligibility, claims work, and persists protection. | Another worker must not independently claim the same eligible operation. |
| 2 | The adapter launches bounded provider work outside the database write transaction. | Slow network I/O does not keep the writer lock open. |
| 3 | The provider returns an execution ID, which is persisted before monitoring. | Later reads can observe that same external operation. |
| 4 | The process stops before storing the final result. | Local interruption does not establish provider failure. |
| 5 | Recovery inspects the known operation, validates the result, and commits result plus completion together. | Recovery does not need to launch a replacement merely because the process restarted. |

**Failure boundary:** the provider may accept a launch before its ID is safely recorded. With no known ID, uncertainty remains; local orphan handling can fail the abandoned attempt while retaining the guard. This deliberately blocks a blind duplicate rather than claiming exactly-once execution. See E03–E05.

**Private-source review:** inspect the claim transaction, streaming ID capture, known-ID monitoring, and fresh-runtime orphan tests. Check that retained error context and guards survive local failure.

## Recover a received paid model response after commit interruption

**Scenario:** classification has returned a response, but committing the accepted decision fails.

The response is associated with a local correlation/attempt record and written to a private receipt through temporary write, file synchronization, and atomic replacement. Recovery can inspect the already-received response, verify ownership and current inputs, apply validation, and finalize the relational result without a second model generation.

If the receipt is missing, malformed, or not owned by the current work, recovery cannot treat it as a valid result. An unresolved paid request remains protected. The existence of an explicit correlated retry path does not make arbitrary network retries safe. See E06–E08 and [receipt engineering](ENGINEERING.md).

**Private-source review:** inspect receipt/ownership checks, interrupted-commit tests, malformed/missing receipt cases, and conditions for releasing the local execution slot.

## A person appears under two company associations

**Scenario:** one canonical person appears in prospect inputs for two selected companies.

The database preserves separate person-company associations while retaining a stable person identity and reusable source references. Invitation policy checks person-level suppression and persisted dispatch evidence, not only whether the second association has an invitation record.

After a handoff or unresolved dispatch, another company association must not erase that protection. Operating windows and daily/weekly capacity remain separate controls, including uncertainty across a calendar boundary. A provider acknowledgment records a handoff; it does not establish delivery or acceptance. See E03 and E09.

The recorded synthetic integration scenario uses 150 companies and 450 person-company associations, including simulated waits and restarts. Those counts are test dimensions from the supplied evidence, not real invitations generated by this example. See E10.

**Private-source review:** inspect alias resolution, suppression constraints, reference-aware retention, restart behavior, and calendar-boundary tests. Current provider authentication and full live-pipeline acceptance require separate evidence.
